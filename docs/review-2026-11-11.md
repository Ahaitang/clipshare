## 2. 回环抑制：测试是否真能证明「A→B→A 不回环」

**能证明，判为通过。** 核心测试是 `TestIntegrationNoLoopback`（`internal/engine/integration_test.go:64-107`），
它用两台**真实 HTTP 端口 + 真实 seeds 发现**的引擎（`newPair`，集成测试文件 19-44 行）、假剪贴板，断言：

1. A 复制内容 → B 的剪贴板被写入、B 历史**恰好 1 条**且 `Origin == "devA"`（同时防「server 与 engine 双写」）；
2. B 的日志里 **`广播条目` 出现 0 次**（直接证明 B 没回播）；
3. 等 600ms（多个轮询周期）后 A 的历史条数不变、A 的 `已应用远端条目` 日志 0 次、A 条目的 `RecvAt` **未被刷新**
   （即使 B 回播同内容被去重，`RecvAt` 也会变——测试把这条「隐性回播」也堵住了）；
4. B 的剪贴板最终仍是该内容（没有被二次写入）。

这四条合起来覆盖了「B 回播不同内容」「B 回播相同内容被去重」「B 反复回播」三类回环表现，足够证明不变量。
另有真实双进程旁证（`docs/verification-2026-11-11.md` §5.3）：向一边推送**不同内容**后，另一边历史始终为空，
说明入站条目不会被转发；相同条目重推只触发对端去重（不产生新条目、不回播）。

## 5. 安全

### 5.1 roomKey 的网络暴露面

`grep` 非测试代码后，roomKey 只出现在两处出网位置，且都是 spec 允许的：

- `internal/sync/client.go:118-119`：`Authorization: Bearer <roomKey>`（spec §6 要求）与 `X-Room: model.RoomHash(roomKey)`（hash）；
- mDNS TXT：`internal/discovery/mdns.go:96` 发的是 `room=<roomHash>`，不是 key（`model.RoomHash` = `sha256(key)[:12]`，`internal/model/model.go:42-45`）；
- `/v1/health`：只返回 `nodeId/name/version/roomHash`（`internal/sync/server.go:155-165`），不含 key；
- 没有把 key 放进 URL/query/请求体（`grep` 确认）；错误信息里也没有 key 值。

### 5.2 文件权限

实测「由程序自己创建」的目录与文件（`/tmp/t7/e`，目录事先不存在）：

```text

```

代码位置：`internal/config/config.go:192,201`（dir 0700、tmp 文件 0600 后 rename）、
`internal/history/history.go:222,226`（同上）；备份 `config.json.bak` 也是 0600（`config.go:126`）。

### 5.3 Web UI 只绑回环

- 代码：`cmd/clipshare/main.go:260,263,290-294`（`127.0.0.1:<port+1>`，占用时回退 `127.0.0.1:0`）；
- 实测（`ss -ltn`）：UI 只有 `LISTEN 127.0.0.1:47951`，同步端口是 `LISTEN *:47950`（spec §6 要求监听 `0.0.0.0`）；
- UI 不做鉴权，只绑回环即符合 spec §9。

### 5.4 结论

符合 spec §6/§9 的安全边界（明文 HTTP、内网信任模型、无 TLS/无账号）。

### 5.5 两条风险提示（非实现偏差，供 captain 决定是否处理）

- **O1（low）启动日志会打印完整 roomKey**：`main.go:356-361` 的 `shortRoomKey` 对 `len<=6` 原样返回，而默认 roomKey 正好 6 位，
  所以日志里是完整房间码（README §3 的示例也展示这一点）。本机日志不属「网络发出」，但用户把日志贴到 issue/聊天时会泄露加入凭据。
  建议：默认只打 hash 前 6 位或 key 前 3 位，需要时加 `--verbose` 才打全码。
- **O2（low，spec 层面）默认 roomKey 熵偏低且 hash 公开**：6 位 × 32 字母表 ≈ 30 bit，而 `/v1/health` 无条件公开
  `sha256(key)[:12]`，同网段可离线穷举恢复 key。spec §6 只评估了「hash 不泄露 key 本身」，未考虑低熵；
  不过 spec §6 也已声明「明文传输，同网段可嗅探/注入」，v1 威胁模型本就不防局域网攻击者，故不构成额外突破。
  建议在 README「安全边界」补一句说明，或把默认 key 加长到 ≥10 位（会牺牲口头/手抄便利）。

## 9. 两处裁决与文档一致性（结论：**通过**）

### 9.1 暂停的边界

- design §5 S5（第 134 行）：不广播本机内容、不写本机剪贴板；**远端条目仍会记录进本地历史**，本地复制仍入历史；

- README §6 第 5 条（第 138 行）：`暂停是「外向」开关：不广播本机内容、不写本机剪贴板；但远端条目仍会进入本地历史（历史与剪贴板是两条独立通道，与关闭「自动应用」时的行为一致）。`
  —— 与 design 文案一致。
- 实现：`engine.go:372-377`（本地复制暂停 → 只入历史、不广播）；`384-389`（远端暂停 → 不 apply；此时 `sync.Server` 已把条目 `Add` 进历史）；
  `TestIntegrationPause` 断言「暂停期间条目进历史、剪贴板不变」，`TestS5PausedStillRecordsLocalCopy` 断言本地复制仍入历史。

### 9.2 UI 端口规则

- design §9：UI 端口 = 同步端口 + 1，被占用时回退系统分配并打印实际地址；同步 listener 归 engine、UI listener 归 main。
- 实现：`cmd/clipshare/main.go:260` `net.Listen("tcp", loopbackAddr(syncPort+uiAddrOffset))`，失败 `263` 回退 `127.0.0.1:0`，
  实际地址由 `282` 拼成 `http://<addr>/ui` 并在启动日志打印；`engine.go:182` 独占 `:port`（同步）。
- 实测：`ss -ltn` 同时看到 `127.0.0.1:47951`（UI）与 `*:47950`（同步）；启动日志打印 `本地历史页: http://127.0.0.1:47951/ui`；
  port+1 被占用时回退到随机端口并打印实际地址（`docs/verification-2026-11-11.md` §5.1 的 `34309` 即此路径）。

## 10. Findings（按严重度）

### M1（medium）`SetAutoApply` / `SetMDNS` 在锁外修改共享 `cfg`，与 `saveConfig` 形成数据竞争

- 位置：`internal/engine/engine.go:311-321`（`SetAutoApply`，315 行 `e.cfg.AutoApply = on`）、
  `engine.go:324-344`（`SetMDNS`，328 行 `e.cfg.MDNS = on`）、`engine.go:549-556`（`saveConfig` 里 `e.cfg.Save` → `json.Marshal(c)` 读整个 cfg）。
- 问题：`e.mu` 只保护了 `e.autoApply`/`e.mdns` 两个镜像字段，`e.cfg` 的写入与序列化都在锁外。
  `internal/tray/tray.go:120,122` 的点击回调是 `go t.toggleAutoApply()` / `go t.toggleMDNS()`，
  所以「快速点两个开关」或「连点同一个开关」会并发进入这两个方法：
  - 两个 goroutine 同时写 `e.cfg.AutoApply` / `e.cfg.MDNS`（write/write）；
  - 一个 goroutine 的 `saveConfig` 用 `json.Marshal` 读 cfg 时，另一个在写（read/write）。
  这违反了 `internal/engine/contract.go:27` 的「所有方法都必须并发安全」。
  后果：`config.json` 可能落盘成过期值（开关重启后回弹）；并发 `SetMDNS` 还可能让 `startFinder` 交错，
  旧 `Finder` 未 `Stop` 就被覆盖 → mDNS 公告/订阅 goroutine 泄漏（`engine.go:454-480` 的 stop→New→Start→赋值不是原子的）。
- 复现（已实测，`go test -race` 稳定报警）：


### L1（low）`PushCurrent` 与轮询竞态会让同一内容广播两次

- 位置：`internal/engine/engine.go:276-296`（`PushCurrent` 不做 `MarkSeen`）；`engine.go:358-378`（轮询 `onLocalChange`）。
- 现象：用户刚复制（下一次轮询尚未发生）就点「发送当前剪贴板」时，`PushCurrent` 广播一次；随后轮询把这次复制当成本机变化，
  `onLocalChange` 再广播一次（同一条目、同一个 ID）。对端会按 S6 去重（第二次 202 不 apply），所以**不影响正确性，只是多一次请求**。
- 实测（overlay 探针）：`广播日志条数=2，历史条数=1`，两行日志同 ID `a4dbb165a2af445b`。
- 建议：`PushCurrent` 成功后调用 `e.poller.MarkSeen(content)`（把当前内容并入基线，语义上正是「它已经是最新状态」），
  或在 `onLocalChange` 里对「刚被 PushCurrent 广播过的内容」跳过（前者更简单、无状态）。

### L2（low）`internal/engine/engine.go` 565 行，超过 500 行阈值且无拆分说明

- 位置：`internal/engine/engine.go`（565 行；其余非测试文件最大 366 行）。
- 问题：该文件同时承担「装配 + Start/Stop + Controller 8 个方法 + finder 生命周期 + 配置落盘」；
  虽然注释质量高、逻辑集中，但超过评审约定的 500 行阈值且没有说明理由。
- 建议：机械拆分即可，不改行为——把 finder 生命周期（`startFinder/stopFinder/refreshPeers`，`engine.go:454-501`）
  挪到 `finder.go`，或把 Controller 方法（`Snapshot` 起至 `ClearHistory`，`237-353`）挪到 `controller.go`，engine.go 只留装配与 Start/Stop。

### L3（low）`webui` 把所有 `PullEntry` 错误映射成 404，与「只在找不到条目时报错」不完全一致

- 位置：`internal/webui/webui.go:84-86`；契约见 `internal/engine/contract.go:36-39`。
- 问题：`engine.PullEntry` 除了「id 不存在」，还会返回 `ErrNotStarted`（`engine.go:405-406`）与写剪贴板失败（`408-409`）；
  Web UI 一律回 404（`{"error":"写入剪贴板失败: …"}`），语义会误导调用方（把内部故障当「条目不存在」）。
- 建议：给 engine 增加可判定的 `ErrEntryNotFound`（`errors.New` 包装），webui 用 `errors.Is` 区分：
  找不到 → 404；其它 → 500。改动小，且让契约注释与实现一致。

### L4（low）启动日志打印完整 roomKey（默认 6 位）

- 位置：`cmd/clipshare/main.go:356-361` `shortRoomKey`（`len <= 6` 原样返回）、`192` 打日志；
  README §3 示例（第 88 行）也展示完整 `房间码: 6adeyu`。
- 说明：这是刻意的可用性设计（多机不通时第一件事就是核对房间码），不违反 spec §6（不属网络发送）；
  但日志被贴进 issue/聊天就等于泄露加入凭据。建议默认只打 hash 前 6 位或 key 前 3 位，`--verbose` 时再打全码。

## 11. 非缺陷观察（避免后续误判为 bug）

1. **S6 重复入站会刷新既有条目的 `RecvAt` 并置顶**：`history.go:125-131` 的刻意行为，`e105559` 已把 spec §5 S6 精确化为
   「不新增条目、不写剪贴板；既有同内容条目会被置顶并刷新 `RecvAt`」，实现与文档一致。
2. **暂停时远端条目仍进历史**：`sync.Server` 先 `Add` 再回调 engine，engine 只能在 `apply` 层拦截写剪贴板；spec §5 S5 已写明这是刻意选择。
3. **配置文件损坏会重置 `roomKey`/`deviceId`**：spec §10 + README §159/§189 已写明「重建后需要重新对齐房间码」。
4. **同机两进程共享 X 剪贴板**：`autoApply` 开启时，A 应用远端内容会被 B 的轮询当成本机复制（`origin=B`），属同机模拟假象，
   `docs/verification-2026-11-11.md` §5.4/§5.5 已说明。
5. **`refreshPeers` 目前只有集成测试使用**（`engine.go:493-501`），注释已注明「供测试与将来」，不是死代码但未被产品路径调用。
6. **版本链路没有回归测试锁定 main 的赋值顺序**（见 §7 小建议）。
